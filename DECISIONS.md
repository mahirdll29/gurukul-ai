# Build decisions

- Plan: keep the existing `/server/src` and `client/src` layout, complete the product in the requested order, and verify each stage with the available typecheck, build, and test commands.
- The supplied Change Notice is not present in the workspace; this build brief takes precedence over the available PRD.
- Phase 0 schema, seed, login, and environment checker already exist. They will be extended rather than rebuilt.
- The workspace has no Git metadata, so per-step commits cannot be created here.
- The npm registry is unreachable from this environment: `npm view zod version` did not return. Do not install new packages until each has been verified as instructed.
- Existing server and client directory layout differs from the PRD's illustrative layout only in that files.ts currently contains multiple route concerns. Keep the existing layout and split routes when practical.
- Client JWT storage remains `localStorage`, as required by the build instructions; this is retained from Phase 0.
- Gemini `gemini-embedding-2` does not accept `task_type`; use explicit text task prefixes as documented, with the same document prefix for all units and a query prefix for searches.
- No Google font stylesheet links will be used. Self-hosted Fontsource packages cannot be added until npm registry verification is available; the current visual step uses system fallbacks meanwhile.
- Known limitation from the PRD: GC can remove derived edges when it purges a source version; storage objects written before a later DB transaction failure can remain orphaned in v1.
- Step 0 replaced the Phase 0 welcome page with the Gurukul-AI sign-in screen and navigation shell. The Files and basic version-history views are connected to existing API routes; several remaining pages are still incomplete.
- Vite needs `resolve.preserveSymlinks=true` in this Windows workspace to avoid `EPERM` when resolving the client entry file.
- The app has no self-hosted Fontsource assets yet because those package names could not be verified through `npm view`; the visual CSS currently uses system font fallbacks.
- `helmet`, `express-rate-limit`, `zod`, `lucide-react`, and Supertest were not added. Manual security headers remain in place; new endpoints validate their inputs by hand. Vitest was added in Phase 9 after registry access was available.
- `npm run check:env` found no missing required variable names, but the configured database, storage, and Gemini endpoints failed their connectivity checks. External-service acceptance checks could not be run.
- The available Neon Object Storage documentation endpoint could not be reached via the web documentation tool. The existing S3 client configuration follows the required `forcePathStyle: true` and AWS SDK S3 commands, but object-storage behavior still needs an actual round-trip check.
- Phase 1 adds a durable ingestion queue in PostgreSQL rather than introducing a queue service. Upload/version creation and job enqueue now share a transaction; workers use expiring leases, bounded retry backoff, and idempotent unit writes. `WORKER_MODE=embedded` preserves the current single-process behavior; `external` supports separate workers. The queue migration and API/worker code typecheck and build, but lease recovery and concurrent-worker behavior still require a live Postgres acceptance run.
- Phase 2 adds signed direct PUT sessions, server-side streamed SHA-256/signature checks, and reuses the same `registerUploadedBlob` path as multipart uploads. Session completion is idempotent and garbage collection only removes old keys under `staging/`. Bucket CORS remains provider-dependent and must be confirmed against the configured storage endpoint; integration upload tests need live S3-compatible storage. The client computes a browser digest, supports sequential multi-file upload with a progress bar, and falls back to multipart if init or direct PUT fails.
- Phase 3 adds a unit-testable monthly storage-cost estimator, scoped cold-eligibility aggregation, and pre-transfer/direct-upload counters. Tiering is simulated; no real storage class mutation occurs. `npm run typecheck` and `npm run build` pass after the server and UI changes; data-dependent estimates still need validation against a populated database.
- Phase 4 adds JSON request/access logging, request IDs, queue/worker health data, professor-only `/api/ops/metrics`, and Dockerfiles/Compose. `docker compose config --quiet` passes. The Docker CLI is installed, but the Docker Desktop Linux engine is not running, so image build/run could not be verified. Compose reads the existing root `.env` with an optional `server/.env` override; no credentials are included in the new files.
- Phase 5 adds a GIN-indexed English `tsvector` and shared hybrid retrieval with Reciprocal Rank Fusion. If embedding retrieval fails, keyword results are returned with `degraded=true`; assistant requests with no relevant units return a fixed response without calling Gemini. Retrieval SQL retains the existing ownership and classroom-share predicates. Validation is typecheck/build only until a migrated database is available.
- Phase 6 adds quiz attempt/review migrations and routes, server-side grading, a pure review schedule, a student Study page, and quiz submission/history UI. Generated quiz questions have no durable source-file identifiers, so weak topics are grouped by quiz file; the question locator is retained in the generated quiz JSON.
- Phase 7 adds anchored annotations and a file-viewer section-notes panel. Carry-over matches hashes against the immediately previous version and marks unmatched annotations outdated; PDF annotations use a typed page locator. End-to-end permission and UI behavior needs a populated database to verify.
- Phase 8 adds non-blocking classroom usage logging and professor-only classroom analytics with distinct-student topic thresholds. Query text is truncated to 200 characters for aggregation and never returned by analytics. The insight charts are lightweight CSS bars; analytics privacy behavior still needs live database acceptance testing. `ANALYTICS_MIN_USERS` defaults to 3.
- Phase 9 adds Vitest unit coverage for queue backoff, RRF, review scheduling, analytics tokenization/privacy thresholds, storage cost math, hashes/magic bytes, unit diffs, and in-memory DOCX/PPTX parsing. The parser test exposed a real PPTX bug: `fast-xml-parser` stores attributes in the `:@` property when `preserveOrder` is enabled; slide relationships and slide IDs now read that representation. Database integration tests apply migrations in an isolated temporary schema and skip if `DATABASE_URL` is absent or unreachable; they exercise queue claims/recovery/dead-lettering, basic permission cases, and dedup scope. We could not verify integration tests against a live database in this environment; API-level search/assistant and analytics endpoint authorization coverage remains a limitation without an HTTP test harness.
